### Hedef dizin (targetDir)

Öncelik sırası: `--cwd` bayrağı > config'deki `targetDir` > çalışılan dizin. Paneldeki dizine (sağ sütun "Hedef dizin") ya da "Dizini değiştir"e tıklayınca **klasör seçici** açılır (2026-10-09; eskiden yol elle yapıştırılıyordu) — `GET/POST /target-dir` (src/server.ts, src/index.ts). Seçince: (1) dizin var mı/klasör mü diye doğrulanır, (2) çalışan sürecin hedefi (`cwd`, artık `let`) güncellenir — **sıradaki görev** yeni dizine yazar, o an çalışan koşuyu etkilemez, (3) `config.json`'a yazılır (alan yoksa eklenir, varsa üzerine yazılır) — böylece bir daha config.json'ı elle açmaya gerek kalmaz. ### Bağlantı dayanıklılığı (yük altındaki vLLM, 2026-10-19)

Kullanıcının ortamında model sunucusu vLLM, önünde düzgün yük dengeleyici/kuyruk yok → 503, zaman aşımı, akışın yarıda kesilmesi. Amaç: ajan durmasın, sürekli denesin. Kod: `src/resilience.ts` (ayarlar, sınıflandırma, bekleme) + `src/runAgent.ts` (`executeQuery` bekçi/hata yakalama, `executeWithRetry` döngü). **Sahte vLLM benzeri sunucuyla her hata türü üretilip doğrulandı (gerçek vLLM'de denenmedi).**

- **İki katman.** (1) Claude Code'un kendi içi: tek isteği süreç kapanmadan yeniden dener — `CLAUDE_CODE_MAX_RETRIES` (varsayılan **10**, 15'in üstünü CLI uyarıyla 15'e indirir; `CLAUDE_CODE_RETRY_WATCHDOG` ile sınır kalkar ama başka davranışları da değiştirdiği için kullanılmıyor). Yeniden denenenler: 408, 409, 429, 5xx, bağlantı hataları. Akış ortası kopmada önce akışlı tekrar, sonra akışsız istek. Bize yalnızca `system/api_retry` mesajı gelir → `api_retry` olayı (panelde balonda tek satır "⏳ … istek yeniden deneniyor (2/10)", art arda gelenler aynı satırı günceller). (2) CLI pes edince hata bize gelir → dış döngü oturumu SÜRDÜREREK (resume) yeniden dener, varsayılan sınırsız.
- **SDK hatayı nasıl veriyor (ölçüldü):** CLI denemeleri bitince önce `assistant` mesajı (`error: server_error|rate_limit|model_not_found|authentication_failed|unknown…`, metin "API Error: 503 …" / "Request timed out" / "Unable to connect to API (ECONNRESET)"), sonra `result` `subtype:"success"` ama **`is_error:true`**, sonra iterator "Claude Code returned an error result: …" atar. - **Sınıflandırma (`classifyError`)**: geçici (503/502/504/529/429/408/5xx, zaman aşımı, kopma, takılma, tanınmayan her şey) → sınırsız; kalıcı (400/401/403/404/413/422, yetki/model yok/istek reddedildi kodları, tur/bütçe sınırı) → **üst üste** `permanentMaxAttempts` (varsayılan 5; araya geçici hata girerse ya da ajan ilerlerse sıfırlanır — yük altında tek tük garip yanıt akışı düşürmesin); `lost_session` ("No conversation found") → kendi açtığımız konuşma kayda geçmediyse önceki konuşmaya, o da yoksa yeni konuşmaya dönülür (eskiden sonsuz döngüydü — ör. dizin değişince resume).
- **Görev TEKRAR gönderilmez**: sahte API ile görüldü — görev, istek sunucuya gitmeden önce konuşma kaydına yazılıyor; eskiden yeniden denemede görev ikinci kez gidiyordu. Kayıt okunamazsa eski davranış (görevle sürdür). CLI resume'da kendisi de "Continue from where you left off." + "No response requested." ekliyor.
- **Bekleme**: `initialDelayMs` her denemede ×2, `maxDelayMs` tavan, `jitter` (varsayılan açık: sürenin yarısı sabit yarısı rastgele — binlerce istemci aynı saniyede geri yüklenmesin). Ajan o denemede ilerlediyse (hatasız assistant mesajı) basamak sıfırlanır. Bekleme Durdur ile anında kesilir.
- **Akış takılma (`stallTimeoutMs`)**: yanıt akmaya başladıktan sonra veri gelmezse. CLI'nin kendi bekçisi var (`CLAUDE_ENABLE_STREAM_WATCHDOG` varsayılan açık, süre `max(CLAUDE_STREAM_IDLE_TIMEOUT_MS, 300000)`) — **ölçüldü: 300 sn'de isteği kesip yanıtı akışsız istekle süreç kapanmadan tamamladı.** Bu yüzden ≥300 sn değer env ile CLI'ye verilir (`buildAgentEnv`), <300 sn ise kendi bekçimiz: `includePartialMessages` ile `stream_event` dinlenir, yalnızca `message_start`→`message_stop` arası kurulur (`system/status` "requesting" ve `api_retry` söker) → ilk baytı bekleme (kuyruk) ve araç çalışması ASLA kesilmez; süre dolunca denemeye özel `AbortController` (koşununki değil — Durdur ayrımı) kesilir → `StallError` → resume. 0 = bizim bekçi kapalı (CLI'ninki 300 sn'de çalışır). ### Çoklu oturum: paralel koşu (tek servis içinde)

Tek serve süreci artık **birden fazla görevi aynı anda** koşturur. Birim = **oturum** (iş parçacığı): her oturumun kendi `SessionRuntime`'ı var (src/runtime.ts) — kendi EventBus'ı, onay/zamanlama yuvası, AbortController'ı, durumu (`idle|running|approval|scheduled|finished|failed|cancelled`, olaylardan `statusAfter` ile türetilir). `RuntimeRegistry` runtime'ları tembel kurar ve oturumun koşu kayıtlarını (`runLogs`, JSONL) diskten **önyükler** → servis yeniden başlasa da geçmiş panelde görünür (yarıda kalmış koşu `cancelled` sayılır).

- **API**: `GET /events?session=ID` (önce geçmiş, sonra `event: ready` {status,busy}, sonra canlı; bilinmeyen oturum 404). `GET /lobby` (SSE: her durum değişiminde tam oturum listesi). `POST /task {task, session?, runAt?}` → `{ok, session, warning?}` — `session` yoksa yeni oturum açılır, varsa o oturum sürdürülür (analist resume). `POST /approval|/schedule|/cancel` gövdesinde **`session` ŞART**. Eski `resumeSessionId` alanı yok.
- **Sınır**: config `maxParallelRuns` (varsayılan 3; zamanlanmış bekleyen görev de yuva tutar). Aşılırsa `/task` 409. Meşgul oturuma ikinci görev verilmez, meşgul oturum silinmez.
- **Aynı `targetDir`**: başka meşgul oturum aynı dizindeyse görev YİNE başlar ama `warning` döner (panel akışa ⚠ yazar) — iki akış aynı dosyalara yazabilir.
- **Onay yalnızca panelden** (sunucu modu): runtime'ın web kanalı `exclusive` — terminal stdin yarışa girmez (cevabın hangi oturuma gittiği belirsiz olurdu). CLI tek görev modunda terminal+panel eskisi gibi yarışır.
- **Panel**: sol sidebar varsayılan AÇIK, birincil gezinme; `/lobby`'den canlı durum rozetleri; sekme başlığında onay bekleyen oturum sayısı `(2) Kurmay — onay bekliyor`. Oturuma tıkla → `resetView()` + `/events?session=` (geçmiş yeniden oynatılırken `replaying` yan etkileri bastırır; `ready` gelince kart/durum uygulanır). **Büyük oturum yükleme (2026-10-20)**: yeniden oynatmada `scrollChat` HİÇ kaydırmaz — her olayda kaydırma tüm sohbeti yeniden ölçtürüyordu (profil: sürenin %92'si; 24 bin olaylık sahte oturum 3 dk'da bitmiyordu → 3,7 sn); `ready`'de bir kez animasyonsuz en alta. Sunucu geçmişten önce `event: history {count}` yollar, panel `#loadInfo` şeridinde "⏳ Oturum geçmişi yükleniyor — n / N olay (%x)" + çubuk gösterir; yükleme sürerken durum rozeti "yükleniyor" kalır (`setStatus` son durumu `replayStatus`'a saklar, `ready`'de uygular — eskiden geçmişteki olaylar yüzünden "çalışıyor" görünüyordu). Yükleme yarıdayken başka oturuma/taslağa geçilirse `replaying` sıfırlanır. Seçili oturum adreste `#<id>` — yenileyince aynı oturum açılır; adres boşsa koşan en yeni oturum (CLI görevi dahil). Oturum boştaysa görev kartı "Bu oturumda yeni görev" (resume), "＋ Yeni oturum" taslağı yeni oturum açar; koşu başlayınca panel o oturuma geçer, diğerleri sürer. Üst çubuktaki dizin GENEL ayardır — koşunun dizini akışın ilk satırında (`📁`).
- `runs/sessions.json`: `{id (bizim UUID), name, createdAt, updatedAt, sdkSessionId?, runLogs[], lastTask?, lastStatus?}`. Eski biçimde `id` SDK kimliğiydi → yüklerken `sdkSessionId = id` (eski oturumlar resume edilebilir). `lastStatus` lobinin, runtime belleğe alınmadan da durum göstermesi için.
- Sahte API ile doğrulandı (gerçek SDK + orchestrator + Playwright): iki oturum paralel → ikisi bağımsız onay bekler, birini onaylamak diğerini etkilemez; sınır reddi; meşgul oturum reddi; iptal yalnız o oturumu keser; aynı oturumda ikinci görev resume (`resumed:true`, sdk kimliği sabit); servis restart sonrası geçmiş diskten; sayfa yenileme; CLI tek görev + terminal onayı. **Gerçek modelle paralel koşu denenmedi** — Ollama `OLLAMA_NUM_PARALLEL=1` ise oturumlar sunucuda sıraya girer.

## İş akışı grafı: düğümler ve geçişler

- **Ajan düğümü** (varsayılan): `file`(persona md), `tools`, `rules`, `skills`, `model`, `requiresUserApproval`, `hooks`. Geçiş için **tam olarak biri**: `next` (koşulsuz) VEYA `verdict` (teftis kararı → onApprove/onReject) VEYA `routes` (structured çıktı alanına göre dallan). (agents.ts bunu doğrular.)
- **routes**: `{field, cases:{deger→hedef}, default}`. analist'in `route` alanı: `implement` → saha-timi, `done` → null (akış biter). **Rota akışı bitirse bile onay ATLANMAZ** (eskiden atlanıyordu): `endsFlow` bayrağıyla onay sorulur — panelde kart "kod değişikliği gerekmediğini söylüyor" başlığı + **Bitir** / **Hayır, yeniden planla** butonlarıyla çıkar, zamanlama satırı gizlenir. Onay=akış biter, red=gerekçe `ctx.feedback`'e gidip aynı ajan yeniden koşar. Sebep: resume'lu 2. prompt'ta analist önceki turun diske yazılmış değişikliklerini görüp "zaten karşılanmış" deyip akışı sessizce bitiriyordu. Saha timine "yine de gönder" butonu bilinçli olarak YOK — `route=done`'da `file_plan` boş olur, saha plansız koşardı.
- **Command düğümü** (`type:"command"`): LLM değil, deterministik build adımı. `{command, parent?:{path,command?}, onSuccess, onFailure}`. build.ts: saha'ın `changes[].file`'lerinden değişen repoları çıkarır (dosyanın targetDir altındaki en üst klasörü = repo), `parent` değişmişse önce onu build eder, sonra değişen servisleri; exit code'a göre onSuccess/onFailure (hata → saha'a log geri bildirimiyle döner). Modül listesi TUTULMAZ (otomatik).
- **Fanout düğümü** (`type:"fanout"`): LLM değil, repo başına dağıtım kapısı. `{agent, maxConcurrency?, parent?, next}`. En son `file_plan` (analist) dosyanın targetDir altındaki en üst klasörüne göre (build.ts ile aynı kural; kökteki dosyalar `"."`) repolara bölünür, `agent`'ın repo başına **ayrı kopyası** koşar — kaç kopya olacağına KOD karar verir. Sıra: `parent` (plandaysa) tek başına → diğer repolar eş zamanlı (`runLimited`, `maxConcurrency`; 0/yok = sınırsız) → `"."` en sonda tek başına (yazma kapsamı tüm dizin). Kopya anahtarı `"<ajan>@<repo>"` (panel olayları bununla), prompt'ta plan yalnızca o reponun dilimi + "Kapsamın" bölümü. **Yazma kapsamı sert**: `runAgent(..., {writeScope})` Write/Edit/MultiEdit/NotebookEdit'i repo dışına PreToolUse SDK callback hook'uyla engeller (Bash hâlâ yazabilir). Sonuçlar `mergeWorkerResults` ile tek çıktıya birleşir (diziler birleşir, metinler `[repo]` etiketli; `changes[].file` repo önekiyle normalize; structured gelmeyen repo için işaretçi değişiklik — build atlamasın) ve işçinin kendi çıktısıymış gibi `ctx.outputs`'a yazılır → inceleme/build tek saha çıktısı görür. **Red/build turunda yalnızca geri bildirimde adı geçen repolar** yeniden koşar (`mentionsRepo`: yol başı/tırnak/köşeli etiket; yol ORTASINDAKİ klasör eşleşmez; eşleşme yoksa hepsi), diğerlerinin önceki sonucu `ctx.fanout`'tan birleşime girer. Bir kopya hata verirse koşu durur (parent düştüyse servisler hiç başlamaz). Plan yoksa ya da tek repoya dokunuyorsa ajan tek kopya normal koşar. **`disabled` fanout'ta ATLAMA DEĞİL**: dağıtım kapanır, ajan bölünmemiş planla tek kopya koşar (paralel/tek kıyası için aynı anahtar). İşçi ajanın kendi kenarı olamaz (agents.ts doğrular), ikinci bir fanout'un işçisi olamaz. Config editöründe fanout eklemek/işçi seçmek `adoptWorker` ile grafı otomatik geçerli tutar (işçinin next'i fanout'a taşınır, işçiye gelen kenarlar + entry fanout'a çevrilir). **Hız uyarısı**: model sunucusu istekleri sırayla işliyorsa (Ollama varsayılanı `OLLAMA_NUM_PARALLEL=1`) paralellik kazandırmaz, kuyruk/zaman aşımı getirir — `maxConcurrency` sunucu kapasitesine göre. Sahte API ile doğrulandı (gerçek SDK + orchestrator): parent önce, eş zamanlılık sınırı (1/2/3/sınırsız ölçüldü), kapsam dışı Write engeli (4 kopyada), yol normalizasyonu, red turunda yalnızca ilgili repo, kapalı fanout = tek kopya. **Gerçek modelle denenmedi.** Aktif `config.json`'da `saha-timi` (saha, `maxConcurrency:3`) bağlı. Config editöründe fanout'un kutusu "Dağıtımı kapat" yazar.
- **effort** (ajan düğümünde): SDK'nin akıl yürütme derinliği (`low|medium|high|xhigh|max`). Aktif configde ayarlı değil (SDK varsayılanı).
- **entry**: başlangıç düğümü. Değiştirmek o adımdan başlatır (ör. planlamayı atlamak için `entry:"saha"`); DİKKAT: analist'e bağlı onay, route ve **resume/oturum da entry'ye bağlıdır** — entry=saha yaparsan resume analist'in değil saha'ın oturumunu sürdürür.

## Hook'lar

- Ajana config'ten **komut-hook**: `"hooks":[{event, matcher?, command, timeout?}]`. src/hooks.ts bunları SDK `hooks`'a derler; runAgent query options'a bağlar (ajanın cwd'sinde çalışır).
- **Sözleşme** (Claude Code semantiği): hook girdisi (tool_name, tool_input, session_id...) stdin'e JSON gelir. `exit 2` = aracı ENGELLE (stderr = modele giden gerekçe); `exit 0` = izin (stdout geçerli JSON ise doğrudan hook çıktısı olarak aktarılır — additionalContext/permissionDecision vb.); diğer çıkış = engellemeyen uyarı.
- Olaylar: PreToolUse, PostToolUse, UserPromptSubmit, Stop, SubagentStop, PreCompact... (**PreToolUse Bash engelleme** ve **Stop tetikleme** canlı doğrulandı.)
- `.claude/hooks/guard-bash.js`: PreToolUse Bash guard (rm -rf/mkfs/shutdown... engeller). `config.hooks.example.json` örnek.
- **`.claude/hooks/guard-readonly.js`: analist'in kod yazmasını engeller** — aktif `config.json`'da analist'e `PreToolUse` `Write|Edit|MultiEdit|NotebookEdit|Bash` matcher'ıyla bağlı. Write/Edit/MultiEdit/NotebookEdit koşulsuz, Bash ise yazma belirtisi taşıyorsa (`>`/`tee`/`sed -i`/`rm|mv|cp|mkdir`/`git add|commit`/`npm install`) exit 2. Okuma/arama/`mvn test` serbest. Sebep: **`tools` listesi yeterli değil** — analist'in araç listesinde Write yokken bile kod yazdığı görüldü; sert kapı bu hook. Yol `node "${configDir}/.claude/hooks/guard-readonly.js"` (eskiden mutlak `D:/work/yaver/...`): hook ajanın cwd'sinde (targetDir) çalıştığı için düz göreli yol kırılır; `${configDir}` config.json'ın klasörüne çevrilir.
- **Java format = C yolu (hook DEĞİL)**: `spotless-maven-plugin` pom'da (`googleJavaFormat` + `<style>AOSP</style>`, `apply` goal'ü `process-sources` fazına bağlı). `build` düğümü `mvn` çalıştırınca format ekstra çağrı olmadan otomatik olur. `testapp/backend/pom.xml`'e eklenip AOSP 4-boşluğun diske yansıdığı doğrulandı.
